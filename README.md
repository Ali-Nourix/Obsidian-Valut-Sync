## چرا Vault Sync؟

Vault Sync یک پلاگین Obsidian است که یک والت را بین دستگاه‌های شما از طریق پروژهٔ Supabase شخصی‌تان همگام می‌کند. برای استفاده، به پروژه، حساب یا کلیدهای سازندهٔ پلاگین نیاز ندارید.

| قابلیت | رفتار |
| --- | --- |
| **همگام‌سازی دوطرفه** | یادداشت‌ها، تصاویر، PDFها، canvasها و فایل‌های داخل محدودهٔ sync |
| **تغییرات زنده** | اعلان‌های Supabase Realtime، بررسی هنگام بازگشت به برنامه و بازهٔ بررسی دوره‌ای |
| **مدیریت تعارض** | ادغام تغییرات سازگار یادداشت‌ها؛ نگه‌داشتن نسخهٔ تعارض برای برخوردهای واقعی |
| **حذف محافظت‌شده** | انتقال به سطل زباله، تأیید حذف گروهی و عدم حذف در اولین sync |
| **رمزنگاری اختیاری** | AES-256-GCM برای محتوا و نام فایل‌ها؛ PBKDF2 با ۶۰۰٬۰۰۰ تکرار برای ساخت کلید |
| **نام‌های فارسی** | یکسان‌سازی Unicode NFC و مدیریت تفاوت بزرگی/کوچکی حروف |
| **دستگاه‌های مختلف** | طراحی برای دسکتاپ، iOS و Android؛ تست واقعی دستگاه پیش از انتشار لازم است |
| **پروژهٔ شخصی** | هر کاربر پروژه و حساب Supabase خودش را دارد؛ بک‌اند مشترک سازنده لازم نیست |

**همگام‌سازی، جایگزین بکاپ نیست.** پیش از اولین نصب، از والت خود نسخهٔ پشتیبان بگیرید.

## نصب و راه‌اندازی — آموزش قدم‌به‌قدم

**مسیر پیشنهادی:** پلاگین را نصب کنید، در پروژهٔ شخصی Supabase یک کاربر sync بسازید و [نصب مستقیم داخل پلاگین](#automatic-setup) را انجام دهید. آماده‌سازی بک‌اند را خود پلاگین انجام می‌دهد.

دو چیز مستقل نصب می‌شوند:

1. **پلاگین:** روی هر دستگاهی که Obsidian دارید.
2. **بک‌اند:** یک‌بار روی پروژهٔ Supabase خودتان، برای استفادهٔ همهٔ دستگاه‌هایتان.

**نیازی به fork، GitHub Actions یا سرور سازنده ندارید.** یک توکن محدود و موقت از حساب خودتان برای نصب می‌سازید؛ برای همگام‌سازی روزمره به آن نیاز نیست.

### پیش از شروع

- از والت بکاپ بگیرید.
- Obsidian حداقل نسخهٔ `1.8.7` داشته باشید.
- یک حساب Supabase و یک **پروژهٔ اختصاصی Vault Sync** داشته باشید؛ از پروژهٔ production وب‌سایت یا برنامهٔ دیگری استفاده نکنید. 
- پروژه باید آماده و فعال باشد. هزینه، ظرفیت و محدودیت‌ها را در پلن خودتان بررسی کنید؛ رایگان‌بودن یا ظرفیت مشخص تضمین نمی‌شود.
- برای build سورس یا ابزارهای توسعه، Node.js **22+** لازم است؛ برای مراحل داخل داشبورد و پلاگین، Node لازم نیست.

### ۱. پلاگین را روی دستگاه اول نصب کنید

**اگر فایل آماده در [Releases](https://github.com/Ali-Nourix/Valut-Sync/releases) موجود است:**

1. فایل‌های `main.js`، `manifest.json` و `styles.css` را از همان نسخه بگیرید.
2. آن‌ها را در پوشهٔ زیر داخل والت قرار دهید:

```text
<vault>/.obsidian/plugins/vault-sync/
├── main.js
├── manifest.json
└── styles.css
```

3. در Obsidian به **Settings → Community plugins** بروید؛ در صورت نیاز Restricted mode را خاموش و Vault Sync را فعال کنید.

> `Code → Download ZIP`، سورس پروژه است؛ با بستهٔ آمادهٔ پلاگین فرق دارد. وقتی Release آماده وجود ندارد، سورس به build نیاز دارد.

**برای امتحان شاخهٔ فعلی `Release`، تا زمانی که بستهٔ آماده منتشر نشده:**

```bash
git clone --branch Release https://github.com/Ali-Nourix/Valut-Sync.git
cd Valut-Sync
npm ci
npm run build
```

بعد سه فایل بالا را از پوشهٔ پروژه به پوشهٔ پلاگین کپی کنید. تا وقتی مخزن خصوصی است، clone فقط برای حساب‌های دارای دسترسی ممکن است. نام مخزن عمداً در دستور همان `Valut-Sync` فعلی است.

[BRAT](https://github.com/TfTHacker/obsidian42-brat) نیز بعد از فراهم‌شدن Release مناسب، مسیر جایگزین نصب است. نام مخزن یا شاخه را با وجود یک بستهٔ نصب‌شدنی اشتباه نگیرید.

### ۲. پروژهٔ Supabase خودتان را بسازید

1. وارد [Supabase Dashboard](https://supabase.com/dashboard) شوید.
2. یک پروژهٔ **اختصاصی و خالی** برای Vault Sync بسازید و صبر کنید تا آماده شود.
3. شناسهٔ ۲۰ کاراکتری پروژه (**Project reference / Project ID**) را از تنظیمات پروژه یا آدرس داشبورد بردارید؛ بعداً در پلاگین وارد می‌کنید.

این پروژه متعلق به خودتان است؛ هزینه و ظرفیت آن به پلن Supabase شما بستگی دارد.

### ۳. در همان پروژه یک کاربر sync اضافه کنید

1. پروژهٔ خودتان را باز کنید و به **Authentication → Users** بروید.
2. **Add user → Create new user** را انتخاب کنید؛ نه **Send invitation**.
3. در **Email address**، ایمیل حساب sync خودتان را بنویسید.
4. در **User Password**، یک رمز مستقل و قوی با حداقل ۱۲ کاراکتر تعیین کنید. این رمز برای ورود به sync است، **نه رمز حساب اصلی داشبورد Supabase**.
5. گزینهٔ **Auto confirm user?** را فعال نگه دارید و **Create user** را بزنید.
6. مطمئن شوید کاربر در فهرست **Users** همان پروژه دیده می‌شود.

در این روش منتظر ایمیل دعوت یا تأیید نمی‌مانید. در همهٔ دستگاه‌ها با **همین ایمیل و رمز** وارد شوید؛ برای دستگاه دوم کاربر جدا نسازید. اگر کاربر مناسب از قبل دارید، همان را استفاده کنید و رمز آن را تغییر ندهید.

**نکته:** حسابی که با آن وارد داشبورد Supabase می‌شوید با کاربری که اینجا داخل پروژه می‌سازید متفاوت است. اگر دکمهٔ ساخت کاربر غیرفعال است، باید با حساب دارای اجازهٔ ساخت کاربر در همین پروژه وارد شوید.

### ۴. نصب را از داخل پلاگین کامل کنید

1. طبق [راهنمای توکن محدود](#setup-token)، یک Scoped PAT موقت برای **همین پروژه** با سه دسترسی مشخص‌شده بسازید.
2. در تنظیمات Vault Sync، **نصب مستقیم با توکن محدود خودتان** را باز کنید؛ شناسهٔ پروژه و توکن را وارد کنید.
3. مدیریت موقت همین پروژه را تأیید و **اتصال به Supabase** را بزنید.
4. نام پروژه را بررسی کنید، شناسه را برای تأیید مقصد دوباره بنویسید و اختصاصی‌بودن پروژه را تأیید کنید.
5. در **حساب sync**، گزینهٔ **استفاده از حساب موجود** را انتخاب کنید؛ ایمیل و رمز کاربر مرحلهٔ قبل را وارد کنید.
6. **راه‌اندازی Vault Sync** را بزنید و تا پایان آماده‌سازی صبر کنید. پلاگین تنظیمات لازم را آماده و اتصال را روی دستگاه اعمال می‌کند؛ حساب موجود دوباره ساخته یا password-reset نمی‌شود.
7. یک والت جدید بسازید یا والت موجودتان را انتخاب کنید. برای والت جدید، اگر رمزنگاری می‌خواهید، عبارت عبور را تعیین و برای دستگاه‌های بعدی نگه دارید.
8. در Supabase، توکن نصب را **Revoke** کنید؛ دیگر برای sync به آن نیاز ندارید.

**توکن را فقط در پنجرهٔ نصب وارد کنید، نه فیلد Publishable key، وب‌صفحه، issue یا chat.** رمز حساب اصلی Supabase و کلید secret/service_role را وارد نکنید. گزینهٔ یادآوری کلید رمزنگاری روی دستگاه غیرقابل اعتماد مناسب نیست.

### ۵. دستگاه دوم را اضافه کنید

1. همان نسخهٔ پلاگین را روی گوشی یا کامپیوتر دوم نصب کنید.
2. **همان URL و publishable key** را وارد کنید.
3. با **همان حساب sync** وارد شوید.
4. والتِ ساخته‌شده در دستگاه اول را **انتخاب کنید؛ والت جدید نسازید.**
5. اگر رمزنگاری روشن است، عبارت عبور همان والت را وارد کنید.

برای دستگاه دوم نصب بک‌اند را تکرار نکنید؛ پروژه، کاربر یا توکن نصب جدید لازم ندارید.

### ۶. اولین همگام‌سازی را آزمایش کنید

- Obsidian را روی هر دو دستگاه باز و **Sync now / همگام‌سازی اکنون** را اجرا کنید.
- یک یادداشت آزمایشی روی دستگاه اول بسازید؛ ظاهرشدنش روی دستگاه دوم را بررسی کنید.
- همان یادداشت را روی دستگاه دوم ویرایش و برگشت تغییر را بررسی کنید.
- یک فایل کوچک اضافه کنید و گزارش sync را ببینید.
- قبل از استفادهٔ جدی، قطع شبکه و تعارض یک یادداشت آزمایشی را هم امتحان کنید.

اولین sync برای نگه‌داشتن فایل‌های موجود دو طرف طراحی شده و چیزی را حذف نمی‌کند. اگر فایل‌ها تفاوت داشته باشند، ممکن است نسخهٔ تعارض ساخته شود. تا کامل‌شدن sync از حذف گروهی فایل‌های اصلی خودداری کنید.

**اگر دستگاه جدید منتظر فایل است:** Obsidian را روی یکی از دستگاه‌های قبلی هم باز کنید. Supabase اینجا relay است، نه آرشیو دائمی؛ دستگاه قبلی باید محتوای لازم را ارسال کند.

## نصب مستقیم داخل پلاگین — بدون سرور واسط

آماده‌سازی بک‌اند داخل پلاگین انجام می‌شود؛ کاربر نیازی به اجرای دستور یا کپی کد ندارد. هیچ OAuth app، Client Secret، Cloudflare، URL سرویس نصب یا توکن سازنده لازم نیست. پلاگین مستقیماً با Management API رسمی Supabase و Auth API **همان پروژهٔ انتخاب‌شده** ارتباط می‌گیرد.

### راهنمای وب استاتیک

فایل [`docs/setup/index.html`](docs/setup/index.html) را دانلود و محلی در مرورگر باز کنید. همین فایل بدون تغییر روی GitHub Pages یا هر میزبان استاتیک قابل ارائه است؛ در این تغییر سایت عمومی یا GitHub Pages فعال نشده است. صفحه هیچ اسکریپت، فرم دریافت توکن، analytics، درخواست API یا ذخیره‌سازی ندارد. دکمه‌ها فقط داشبورد و صفحهٔ Access Tokens خود Supabase را باز می‌کنند؛ پروژه، scope و توکن را خود کاربر در داشبورد انتخاب می‌کند، نه اینکه این صفحه آن‌ها را خودکار تنظیم کند.

### ۱. پروژهٔ اختصاصی موجود و آماده

در داشبورد Supabase یک پروژهٔ خالی بسازید و تا آماده‌شدن صبر کنید. شناسهٔ ۲۰ کاراکتری پروژه را بردارید. ساخت پروژه در این نسخه داخل پلاگین انجام نمی‌شود؛ این انتخاب اجازه می‌دهد توکن را از ابتدا **فقط به همان پروژه** محدود کنیم و دسترسی سازمانی یا ساخت پروژه نخواهیم. هزینه و سهمیهٔ پلن خودتان را بررسی کنید.

<a id="setup-token"></a>

### ۲. Scoped PAT کوتاه‌عمر بسازید

[Access Tokens](https://supabase.com/dashboard/account/tokens) → ساخت توکن جدید → **Scoped، نه Legacy**. نام پیشنهادی `Vault Sync setup`، انقضای کوتاه مناسب نصب، و scope فقط پروژهٔ بالا. توکن‌های Scoped طبق [مستند رسمی](https://supabase.com/docs/guides/platform/personal-access-tokens) با `sbp_fc` شروع می‌شوند. پیشوند فقط نوع قالب را نشان می‌دهد؛ اثبات نمی‌کند که scopeها را درست انتخاب کرده‌اید.

| Permission در داشبورد | Access | دلیل |
| --- | --- | --- |
| Project Settings | Read | بررسی نام، شناسه و وضعیت پروژه |
| Database | Read-write | بررسی تداخل، آماده‌سازی بک‌اند و تأیید نصب |
| API Keys | Read | گرفتن کلید عمومی اتصال |


**برای مسیر پیشنهادی بالا، API Key Secrets را فعال نکنید:** کاربر sync را خودتان در داشبورد ساخته‌اید و در پلاگین «استفاده از حساب موجود» را می‌زنید. اگر عمداً ساخت خودکار کاربر را انتخاب کنید، فقط آن حالت به API Key Secrets: Read هم نیاز دارد.

**لازم نیست:** Projects (account-wide)، Organizations، billing، Organization Projects، Auth Config یا Project Settings: Read-write. فهرست همهٔ پروژه‌ها درخواست نمی‌شود. این نسخه ثبت‌نام کل پروژه را تغییر نمی‌دهد و کلید API جدید نمی‌سازد یا rotate نمی‌کند.

Database: Read-write همچنان دسترسی قدرتمندی است؛ روی پروژهٔ production مشترک استفاده نکنید. توکن فراتر از نقش حساب شما دسترسی ایجاد نمی‌کند. یک توکن Scoped که پروژه یا مجوز لازم را ندارد، با خطای مجوز رد می‌شود؛ از Legacy برای دورزدن خطا استفاده نکنید.

### ۳. توکن فقط داخل پنجرهٔ نصب

1. در تنظیمات Vault Sync، «نصب مستقیم با توکن محدود خودتان» را باز کنید.
2. شناسهٔ پروژه و Scoped PAT را در فیلد مخفی پنجره وارد کنید. توکن را در وب‌صفحه، `Publishable key`، issue یا chat نگذارید.
3. اعتماد به همین پلاگین و دستگاه برای مدیریت موقت پروژه را تأیید و «اتصال به Supabase» را بزنید.
4. نام و وضعیت پروژه را بررسی کنید، سپس شناسه را دوباره برای تأیید مقصد بنویسید و اختصاصی‌بودن پروژه را تأیید کنید.
5. **استفاده از حساب موجود** را انتخاب کنید و ایمیل و رمز کاربری را که در **Authentication → Users** ساخته‌اید وارد کنید. رمز حساب داشبورد لازم نیست. رمز حساب موجود reset نمی‌شود.
6. «راه‌اندازی Vault Sync» را بزنید. پلاگین سازگاری و امنیت پروژه را بررسی می‌کند، بک‌اند را آماده می‌کند و ورود کاربر sync را می‌آزماید.
7. اتصال عمومی روی دستگاه اعمال می‌شود؛ والت موجود را انتخاب یا والت جدید بسازید. عبارت عبور رمزنگاری محلی می‌ماند و در نصب بک‌اند استفاده نمی‌شود.

### ۴. توکن نصب را Revoke کنید

پس از نصب از همان صفحهٔ [Access Tokens](https://supabase.com/dashboard/account/tokens)، توکن را **Revoke** کنید. برای sync یا دستگاه دوم لازم نیست. PAT و کلید مدیریتی فقط در حافظهٔ نشست نصب‌اند؛ در تنظیمات، فایل، localStorage یا لاگ ذخیره نمی‌شوند. PAT هنگام پایان/خطا/بستن پنجره پاک می‌شود و نشست ۱۵ دقیقه‌ای دارد. پاک‌کردن referenceهای JavaScript تضمین forensic zeroization یا revoke در Supabase نیست؛ دستگاه آلوده و پلاگین مخرب هنوز خطر دارند.

بستن پنجره جلوی مراحل بعدی را می‌گیرد، ولی درخواستِ ارسال‌شده ممکن است کامل شود. schema، حساب یا تغییر انجام‌شده خودکار rollback نمی‌شود. اگر بعد از نصب حساب، اتصال دستگاه خطا داد، مسیر دستی را با همان URL، کلید عمومی و حساب ادامه دهید؛ حساب جدید یا reset رمز نسازید.

## معماری: relay، نه بکاپ

```text
Obsidian device A ──┐
                   ├── Your Supabase project ── index + private transit bucket
Obsidian device B ──┘                         └─ Realtime notifications

Optional setup only:
Obsidian wizard ── scoped PAT (temporary, on-device) ── Supabase Management / Auth APIs
```

- هر دستگاه، نسخهٔ محلی، index سرور و وضعیت موردتوافقِ sync قبلی را مقایسه می‌کند.
- نوشتن‌ها با compare-and-set انجام می‌شوند تا تغییر هم‌زمان بی‌صدا بازنویسی نشود.
- نسخهٔ پایهٔ یادداشت برای merge روی دستگاه نگه‌داری می‌شود.
- محتوا فقط وقتی دستگاه دیگری نیاز دارد ارسال می‌شود. پس از دریافت و تأیید دستگاه‌ها، blobهای بدون نیاز واجد پاک‌سازی می‌شوند؛ پاک‌سازی به اجرای کلاینت و مهلت محافظتی وابسته است، نه حذف آنی تضمین‌شده.
- دستگاهی که ۳۰ روز دیده نشده فراموش می‌شود؛ هنگام برگشت، محتوای لازم را درخواست می‌کند.

منطق و جدول کامل تصمیم‌ها در [sync-design.md](docs/sync-design.md) مستند است.

## امنیت و حریم خصوصی

| داده یا کلید | جای درست | نکته |
| --- | --- | --- |
| Project URL و publishable/anon key | تنظیمات پلاگین | دسترسی به داده‌ها همچنان به ورود و RLS وابسته است |
| نشست کاربر و شناسهٔ دستگاه | storage محلی دستگاه | با پروژهٔ تنظیم‌شده scope می‌شود، نه داخل `data.json` |
| Scoped PAT و کلید مدیریتی | فقط حافظهٔ پنجرهٔ نصب مستقیم | نه در ریپو، تنظیمات، فایل یا screenshots؛ بعد از نصب PAT را Revoke کنید |
| عبارت عبور رمزنگاری | دستگاه کاربر | به سرویس نصب فرستاده نمی‌شود |
| کلید رمزنگاریِ remembered | storage محلی Obsidian | keychain سیستم‌عامل نیست؛ روی دستگاه غیرقابل اعتماد یادآوری را خاموش کنید |

- با رمزنگاری روشن، محتوای فایل و نام فایل‌ها برای سرور قابل خواندن نیستند؛ اندازه و زمان‌ها و بعضی metadata همچنان قابل مشاهده‌اند.
- رمزنگاری سرور/انتقال، دستگاه آلوده، پلاگین مخرب، یادداشت محلی یا merge baseهای محلی را امن نمی‌کند.
- اگر کلیدی قبلاً منتشر شده، **اول revoke/rotate** کنید؛ حذف فایل یا `.gitignore` تاریخچه و بکاپ‌ها را پاک نمی‌کند.
- اسکن secret روی فایل‌های تغییرکرده، تضمین ممیزی تمام تاریخچه، لاگ‌ها و artifactها نیست.

اگر والت را با Git نگه می‌دارید، state و merge baseهای این دستگاه را commit نکنید:

```gitignore
.obsidian/plugins/vault-sync/state/
.obsidian/plugins/vault-sync/base/
```

تنظیمات، تصاویر و خروجی‌های خطا را قبل از به‌اشتراک‌گذاری بررسی کنید. هنگام گزارش مشکل، توکن، رمز، session، عبارت عبور یا محتوای خصوصی یادداشت نفرستید.

## رفع مشکل

| مشکل | کاری که انجام دهید |
| --- | --- |
| `main.js` در ZIP نیست | ZIP سورس گرفته‌اید؛ build کنید یا بستهٔ آمادهٔ Release را بگیرید |
| «پایگاه داده آماده نیست» | نصب مستقیم را برای پروژهٔ اختصاصی درست کامل کنید و اتصال را دوباره آزمایش کنید |
| ورود ناموفق است | حساب sync داخل همان پروژه، رمز و تأیید ایمیل را بررسی کنید؛ حساب داشبورد متفاوت است |
| نصب مستقیم وصل نمی‌شود | شناسهٔ پروژه و Scoped PAT، تاریخ انقضا و مجوزهای جدول بالا را بررسی کنید؛ این مسیر سرویس `/health` یا OAuth ندارد |
| پنجرهٔ OAuth یا installer URL می‌بینید | نسخهٔ قدیمی نصب است؛ آخرین `Release` را build و سه فایل پلاگین را جایگزین کنید |
| پروژه آماده نیست | تا `ACTIVE_HEALTHY` شدن صبر کنید و پروژه‌ها را تازه‌سازی کنید |
| جدول هم‌نام وجود دارد | یک پروژهٔ اختصاصی خالی استفاده کنید؛ روی جدول برنامهٔ دیگر نصب نکنید |
| حساب قبلاً وجود دارد | رمز درستِ همان حساب را وارد کنید؛ نصب‌کننده رمز را reset نمی‌کند |
| فایل‌ها «در راه» هستند | Obsidian را روی دستگاه قبلی هم باز کنید تا محتوا ارسال شود |
| پروژه متوقف شده است | وضعیت پروژه را در Supabase بررسی و در صورت لزوم Restore کنید |
| فایل بزرگ sync نمی‌شود | حد پلاگین، حد باکت و پلن خود را بررسی کنید؛ پیش‌فرض پلاگین ۵۰ MB است |
| sync روی گوشی متوقف است | Obsidian را باز نگه دارید؛ فعالیت پس‌زمینهٔ موبایل محدود است |
| نسخهٔ تعارض ساخته شده | دو نسخه را بازبینی کنید؛ قبل از پاک‌کردن، محتوای لازم را نگه دارید |

گزارش sync از نوار وضعیت یا دستور **Open sync log / باز کردن گزارش همگام‌سازی** قابل مشاهده است. Reset sync state برای بازسازی مقایسه‌هاست؛ جایگزین بکاپ یا راه‌حل خودکار همهٔ مشکلات نیست.

## محدودیت‌ها

- پوشه‌های مخفی مانند `.obsidian` و `.trash` sync نمی‌شوند؛ تنظیمات، پوسته و پلاگین‌ها per-device می‌مانند.
- استفادهٔ هم‌زمان iCloud و Vault Sync روی همان پوشه توصیه نمی‌شود.
- این سیستم تاریخچهٔ دائمی یا بکاپ سرور ارائه نمی‌کند.
- برای پرشدن دستگاه جدید، ممکن است یکی از دستگاه‌های قبلی باید آنلاین و Obsidian آن باز باشد.
- رفتار پلن، توقف پروژه و سقف فایل‌ها تابع Supabase و تنظیمات پروژهٔ خودتان است.
- نتیجهٔ تست آفلاین، به‌تنهایی تأیید عملکرد واقعی روی همهٔ گوشی‌ها و نسخه‌های Obsidian نیست.

## توسعه و مشارکت

**نیازمندی: Node.js 22+**؛ SDK قفل‌شدهٔ Supabase همین حداقل را می‌خواهد.

```bash
npm ci
npm test                  # suite موجود sync/schema + تست‌های onboarding
npm run test:onboarding   # تست آفلاین و type-check اجزای جدید نصب
npm run build             # type-check و bundle پلاگین
npm run dev               # rebuild هنگام تغییر سورس
npm run preview:onboarding
node --test test/direct-installer.mjs
```

تست‌های نصب مستقیم و رابط با APIهای نمونه اجرا می‌شوند؛ نتیجهٔ آن‌ها تأیید نصب زنده یا CI نیست.

تست‌های نصب، مهاجرت تنظیمات قدیمی و بارگذاری پلاگین از مسیر مستقیم استفاده می‌کنند؛ هیچ سرویس نصب، callback مرورگر یا مسیر deploy قدیمی در این شاخه وجود ندارد. موفقیت تست آفلاین جای آزمون واقعی دسکتاپ/موبایل و پروژهٔ Supabase آزمایشی را نمی‌گیرد. `npm test` (suite آفلاین sync/schema، ۴۶ بررسی بارگذاری پلاگین و ۱۲ تست نصب/رابط) و `npm run build` در محیط محلی Node 24 پاس شدند؛ تست Supabase زنده اجرا نشد. این نتیجه تأیید CI نیست. workflowهای GitHub هنوز Node 20 دارند؛ اصلاح به Node 22 با محدودیت دسترسی اتصال GitHub مسدود شد و باید پیش از انتشار انجام شود.

برای تست زنده از **پروژه و کاربر آزمایشی** استفاده کنید. نام متغیرهای موردنیاز `test:live` عبارت‌اند از `VAULT_SYNC_SUPABASE_URL`، `VAULT_SYNC_SUPABASE_KEY`، `VAULT_SYNC_SUPABASE_EMAIL` و `VAULT_SYNC_SUPABASE_PASSWORD`؛ مقدارهای حساس را امن تزریق کنید، نه در سورس و issue.

```text
src/core/        planner، engine، merge، crypto و scheduler
src/backend/     رابط بک‌اند و پیاده‌سازی Supabase
src/obsidian/    فایل‌ها، state و storage دستگاه
src/onboarding/  نصب مستقیم با Scoped PAT، schema بسته‌بندی‌شده
src/ui/          تنظیمات و پنجره‌های پلاگین
docs/setup/      صفحهٔ راهنمای استاتیک؛ بدون فرم دریافت توکن
supabase/        schema عمومی و نصب‌شدنی
test/           تست‌های آفلاین و سناریوهای sync
```

برای contribution، تغییرات را در شاخهٔ جدا و PR ارائه کنید؛ رفتار قابل بازتولید، نسخهٔ Obsidian/سیستم‌عامل و لاگ پالایش‌شده را همراه تست مرتبط بفرستید. مشکلات و درخواست‌ها در [Issues](https://github.com/Ali-Nourix/Valut-Sync/issues) ثبت شوند؛ credential یا فایل خصوصی نفرستید.
